## Development Environment

The plugin runs inside a Docker Compose stack (WordPress + MySQL). Start it with:

```bash
docker compose up -d
```

WordPress is available at http://localhost:8080. The plugin directory (`lihi-short-url/`) is mounted directly into the container at `wp-content/plugins/lihi-short-url`, so file changes take effect immediately without rebuilding.

## Testing

Tests run inside Docker using a dedicated test database plus separate PHP 7.4 and PHP 8.2 PHPUnit containers built from official `php:*-cli` images. Composer must be run only inside those containers. Each PHP version mounts only `lihi-short-url/`, `tests/`, `patchwork.json`, and `phpunit.xml` read-only under `/app/code`, exposes its version-specific Composer file/lock as `/app/composer.json` and `/app/composer.lock`, and stores `vendor/` plus the WordPress core install in that service's Docker-managed `/app` volume. Dependency installs should not create `vendor-*` or `wordpress-*` directories in the repository working tree.

```bash
make test
```

`make test` intentionally stops the local WordPress / MySQL development services, runs PHP 7.4 and PHP 8.2 sequentially against `db_test`, and stops each PHPUnit container after its run so the host does not need to keep both PHP containers alive at once.

For one PHP version:

```bash
make test74
make test82
```

Manual equivalent:

```bash
docker compose stop wordpress db
docker compose --profile test stop phpunit82
docker compose --profile test up -d --build db_test phpunit74
docker compose --profile test exec phpunit74 composer install --working-dir=/app
docker compose --profile test exec phpunit74 sh -lc 'cd /app/code && /app/vendor/bin/phpunit -c phpunit.xml'
docker compose --profile test stop phpunit74

docker compose --profile test up -d --build db_test phpunit82
docker compose --profile test exec phpunit82 composer install --working-dir=/app
docker compose --profile test exec phpunit82 sh -lc 'cd /app/code && /app/vendor/bin/phpunit -c phpunit.xml'
docker compose --profile test stop phpunit82 db_test
```

The PHP 7.4 container covers the plugin's minimum supported PHP version; the PHP 8.2 container catches compatibility issues on a modern runtime. The latest complete run passes on both versions with 202 tests / 524 assertions. `make coverage` follows the same one-version-at-a-time pattern; `make coverage74` and `make coverage82` generate coverage under `/app/coverage` in the matching container workspace.

## Packaging

GitHub Actions workflow `.github/workflows/package-plugin.yml` runs only on tag pushes. The package job builds `build/lihi-short-url.zip`, validates that the ZIP contains `lihi-short-url/lihi-short-url.php` and `lihi-short-url/readme.txt`, and uploads artifact `lihi-short-url-plugin`; the release job downloads that same artifact and publishes a GitHub Release for the tag. If a release for the tag already exists, the ZIP asset is replaced with `gh release upload --clobber`.

## Translations

Compile `.po` files to `.mo` binaries (requires `gettext` / `msgfmt`):

```bash
make          # compile all .mo files
make clean    # remove compiled .mo files
```

Translation files live in `languages/`. The WordPress.org slug and gettext text domain are `lihi-short-url`.

## Architecture

- `lihi-short-url/lihi-short-url.php` — plugin entry point. The header declares `Text Domain: lihi-short-url` (matching the WordPress.org slug). Registers activation and deactivation hooks whose lifecycle-store factory explicitly requires the exception and token-store files, so hook execution never depends on the later admin-only bootstrap. Both hooks use `transition_activation()` for one complete state transition: remove the epoch before waiting, acquire the shared auth lock within 35 seconds, remove the epoch again under that lock, purge credentials, then either install a fresh random epoch for activation or verify the disabled state for deactivation before releasing the lock. A best-effort fallback separately attempts epoch disable and credential deletion without allowing cleanup errors to escape the WordPress hook; an absent epoch keeps any undeleted tuple unusable, and a foreign lock is never removed. Non-admin requests are rejected via early `return`. Loads `bootstrap.php` only for normal admin execution. The plugin no longer calls `load_plugin_textdomain()` — once published on WordPress.org the directory auto-loads translations from the language pack, and self-hosted environments still pick up the bundled `.mo` files via WP's default loader.
- `lihi-short-url/readme.txt` — canonical WordPress.org readme. Includes WordPress.org metadata, an `External services` section that discloses outbound lihi calls (data sent + ToS / Privacy URLs) per WordPress.org guideline 9, the FAQ / Changelog rendered on the directory listing, and a Description note that the plugin is maintained at `weedgood/lihi-wp-plugin` on GitHub. This file is the source of truth for user-facing plugin metadata; the project root `README.md` is for developers.
- `lihi-short-url/LICENSE` — GPL-2.0-or-later full text. Matches the `License: GPLv2 or later` declared in the plugin header and `readme.txt`.
- `lihi-short-url/uninstall.php` — runs once on plugin deletion (when `WP_UNINSTALL_PLUGIN` is defined). It directly requires the exception and token-store files instead of depending on plugin bootstrap, runs the disabled form of the same complete lifecycle transition, and falls back to independent best-effort epoch disable plus credential deletion. Authentication remains fail-closed even if cleanup encounters a database error; a foreign in-flight lock is never deleted directly.
- `lihi-short-url/bootstrap.php` — loads all includes in dependency order: helper → settings → exceptions → interface → client → token store → service → shorturl-column-ajax → add-shorturl-column. Everything loads unconditionally. The settings page and AJAX actions remain available while disconnected; Short URL UI hooks inside `add-shorturl-column.php` register only when `lihi_is_authenticated()` sees the current activation epoch and one complete credential tuple.
- `lihi-short-url/includes/helper.php` — namespace helpers: `lihi_api_host()`, `lihi_email()`, `lihi_is_authenticated()`, `lihi_site_host()`, `lihi_passthrough_redirect_url()`, `lihi_home_url()`, `lihi_password_reset_url()`, and `lihi_resolve_url()`. `lihi_api_host()` returns the production app/API origin `https://app.lihi.com`; passthrough and password-reset URLs derive from it. `lihi_email()` reads the email from the epoch-fenced atomic credential bundle; `lihi_is_authenticated()` requires the current request's activation epoch plus a complete `{ email, uuid, access_token, refresh_token }` tuple. Both credential probes catch every store failure and degrade to disconnected, so a database lock timeout during bootstrap cannot fatal the whole wp-admin request. The `uuid` field is an opaque server-issued Login-session identifier; there is no separate email option, local UUID helper, or UUID store. Client, service, and store access go through `Lihi_Singletons`.
- `lihi-short-url/includes/lihi-singletons.php` — `Lihi_Singletons`: request-lifetime singleton registry and dependency composition class. `lihi_client()` constructs `Lihi_Client` with only the API base URL; `lihi_token_store()` and `lihi_service()` provide the shared credential store and business service. Matching `*_set()` methods replace or reset instances for tests.
- `lihi-short-url/includes/settings.php` — registers the settings page under Settings → lihi Short URL. Disconnected users see separate Login and Register forms; neither email field is prefilled because no last-known identity is stored. Both are real POST forms targeting `admin-ajax.php`, with hidden action and nonce fields, so the server-side flow remains usable without JavaScript. `wp_ajax_lihi_login` validates `manage_options`, nonce, email, and password, then runs the server-side PKCE login plus authorization-code exchange; the service persists email and all credentials together and the AJAX response returns no tokens to the browser. Auth-lock contention has a distinct HTTP 409 “authentication request is in progress” response instead of being reported as credential persistence failure. `wp_ajax_lihi_register` validates a minimum of six Unicode code points—the same rule used by the JavaScript validator—plus explicit account-creation consent and sends `{ email, hostname, password }`; registration only sends a verification email and never logs the account in or writes the credential bundle. `wp_ajax_lihi_logout` removes the local bundle. `wp_ajax_lihi_dashboard_passthrough` uses protected passthrough only while connected and otherwise returns the public lihi home URL. Passwords are unslashed but otherwise preserved and never stored. Connected rendering calls `get_profile()` to display account role and plan end date; a missing or terminally rejected bundle returns the page to Login/Register. Server diagnostics use `error_log` only when `WP_DEBUG` is true; unexpected `Throwable` values crossing Login or Register are logged by class only, never by exception message, because credential-handling exceptions may contain argument values.
- `lihi-short-url/includes/client/lihi-client-interface.php` — `Lihi_Client_Interface`: unified contract for the lihi Wordpress API under `wordpress/v1`. Unauthenticated methods cover credential login, registration, authorization-code exchange, and refresh-token rotation. Every protected method receives the current access token plus an access fallback callback and retries its own endpoint at most once after a decoded JSON HTTP 401. `GET /user/options` returns create-modal data, `GET /site/find` returns one short URL in `data.site`, and `POST /site/store` creates short links. Browser-facing `GET /passthrough/redirect` is not a client method because it creates a SaaS web session. `POST /mail`, site update/delete, `/posts`, and `/site-urls` are outside the plugin contract. See `docs/lihi-api-endpoints.md`.
- `lihi-short-url/includes/client/lihi-client.php` — production HTTP client. Login sends `{ email, password, code_challenge }`; registration sends `{ email, hostname, password }`; the token endpoint exchanges `{ grant_type: "authorization_code", code, code_verifier }` or rotates `{ grant_type: "refresh_token", uuid, refresh_token }`. Every auth endpoint is successful only when the HTTP status is 2xx and the decoded response has `result: true`; a non-2xx response cannot be accepted merely because its JSON body says success. The server response field `data.token` is normalized by the service to local `access_token`. Protected requests use `Authorization: Bearer ...`; only a decoded JSON HTTP 401 invokes the supplied fallback, after which the same API is retried once. Malformed / non-JSON 401 responses fail closed without refresh. `User Invalid` / `user_not_found` are terminal identity failures, `refresh token invalid` and `code invalid` use dedicated exceptions, 429 maps to `Lihi_Rate_Limit_Exception`, and network / non-2xx / unexpected failure envelopes map to `Lihi_Server_Exception`. Passthrough nonce creation still sends the browser PKCE challenge plus optional target.
- `lihi-short-url/includes/store/lihi-token-store.php` — `Lihi_Token_Store`: persistent, site-scoped credential storage and lifecycle fencing. One non-autoloaded `lihi_auth_tokens` option holds the atomic `{ email, uuid, access_token, refresh_token }` tuple; `uuid` accepts a 16–128 character opaque alphanumeric / `_` / `-` server identifier rather than requiring UUIDv4. `get()` memoizes the normalized tuple for the PHP request, while `get_fresh()` and all concurrency-sensitive service paths query the options table directly. The non-autoloaded `lihi_auth_tokens_lock` is a 45-second renewable DB lease shared by complete Login, Refresh, Logout, conditional cleanup, and lifecycle transitions. Only its current byte-exact owner can atomically renew it; Login renews between remote legs and before persistence, and Refresh renews after the remote response. A successful renewal whose direct read-back does not match immediately compare-deletes the exact renewed value before local ownership is cleared, so it cannot leave a live orphan lease until TTL expiry. A third non-autoloaded option, `lihi_auth_epoch`, contains a random 64-character hex activation generation. `SELECT CONCAT('x', option_value)` distinguishes a present empty row from an absent row; unavailable DB methods, `$wpdb->last_error`, and failed insert/update/delete queries consistently throw `Lihi_Server_Exception`, while `false` is reserved for normal lock contention or guard mismatch. Guarded upserts and compare-and-swap deletes use `CAST(... AS BINARY)` for byte-exact epoch, owner, and raw tuple comparison. Stale, malformed, empty, or implausibly future lock rows can be repaired; waiters stop polling as soon as the observed lease is missing or stale. Every direct mutation invalidates WordPress option caches and the request memo. `transition_activation()` fences before waiting, repeats disable/purge under the same lease, and optionally installs the new epoch. This development implementation recognizes only the current bundle shape and has no legacy-auth compatibility path.
- `lihi-short-url/includes/service/lihi-service.php` — `Lihi_Service`: business logic with injected client and credential store. `login( $email, $password )` verifies its captured activation epoch before acquiring the shared auth lease and again after acquisition, holds it across PKCE Login / token exchange / guarded persistence, renews it between the two remote calls and again before persistence, and releases on every exit. `register()` verifies the epoch but does not create a session; `logout()` uses the same lease to clear the bundle. Every protected workflow uses fresh direct credential reads and supplies a shared fallback that performs single-flight refresh rotation. The Refresh winner renews after the remote response and before validation/persistence; concurrent losers poll for a replacement, stop early on a missing/stale lease, then retry acquisition. Exhausted contention throws `Lihi_Authentication_Busy_Exception`; once Refresh itself is attempted, any failure still clears only the matching Login-session tuple and surfaces the required re-login `Lihi_Token_Invalid_Exception`. Terminal protected `User Invalid`, `user_not_found`, or second-401 failures do not refresh and instead call lock-owned `delete_if_access_token()` so a concurrent successful rotation is preserved. `get_or_create_short_url()` checks `GET /site/find`, then creates with the selected domain/tags and a destination URL containing any UTM parameters. `get_existing_short_url()` never creates; `create_passthrough_nonce()` forwards the browser proof and target.
- `docs/lihi-api-endpoints.md` — lihi API endpoint reference with request/response shapes and error mapping. It intentionally describes API behavior without exposing internal source or documentation locations.
- `lihi-short-url/includes/shorturl-column-ajax.php` — AJAX endpoints for the Short URL column buttons. Handlers validate nonce, item identity, and `read_post`; passthrough additionally requires `manage_options`. All protected actions reject an incomplete credential bundle with HTTP 409 via `lihi_is_authenticated()`. The options handler returns normalized domain and UTM choices. Create parses and sanitizes domain/tags/UTM, writes `lihi_already = 1`, and returns the short URL. Copy never creates; a missing upstream link writes `lihi_already = 0` and returns HTTP 410 / `lihi_missing`. Passthrough validates a 43-character browser challenge plus `/myDomain`, `/profile#utm-setting`, or an absolute target. Common exception mapping returns 401 for an access/refresh session that cannot be recovered, 403 for permissions or unavailable accounts, 409 for disconnected state or a busy auth lease, 410 for a missing link, 429 for upstream throttling, 503 for service failures, and 400/500 for request/unexpected failures.
- `lihi-short-url/includes/add-shorturl-column.php` — UI hooks (enqueue, column registration, attachment detail panel) register only when `lihi_is_authenticated()` confirms the current activation epoch and complete credential bundle. Store errors in this bootstrap-time probe fail closed as disconnected instead of escaping through plugin include and taking down wp-admin. Enqueued button assets use filemtime cache-busting versions. It registers a "lihi Short URL" column for every public post type and Media Library list mode, plus an attachment-detail field. PHP outputs an empty, narrowly allowlisted `.lihi-button-container`; `lihi-button.js` renders Create / Copy controls into it.
- `lihi-short-url/assets/lihi-button.css` — scoped admin styles for the Short URL controls and modals. List-table `.lihi-button-container .button` controls keep Create / Copy / Edit at the default WordPress admin button height so the lihi column does not visually overpower native admin actions.
- `lihi-short-url/assets/lihi-settings.js` — progressive enhancement for the native Login and Register POST forms plus Logout. It intercepts form submission when available, applies the same six-Unicode-code-point Register password rule as PHP, associates local field errors through `aria-invalid` and `aria-describedby`, focuses the invalid field, submits only to the matching nonce-protected AJAX action, clears password fields, and renders text-only inline notices. Successful Login and Logout preserve the success notice for two seconds before reload; successful registration copies the submitted address to Login but remains disconnected. Password-invalid errors may include the allowlisted reset link. The dashboard button uses passthrough only while fully connected; otherwise it opens `https://lihi.io`.
- `lihi-short-url/assets/lihi-button-api.js` / `lihi-short-url/assets/lihi-button-modal.js` / `lihi-short-url/assets/lihi-button.js` — frontend Short URL button stack. WordPress 5.5 compatibility is preserved by enqueueing classic scripts with dependencies (`lihi-button-api` → `lihi-button-modal` → `lihi-button`) instead of ES modules. `lihi-button-api.js` owns the semantic admin-ajax facade (`loadUrlOptions(container)`, `createShortUrl(container, options)`, `copyShortUrl(container)`, `createPassthroughNonce(container, target, challenge, messages)`), so action names, nonce, item id/type payloads, target/challenge validation, JSON error parsing, and the 60-second domain / UTM options cache stay out of UI code. `lihi-button-modal.js` owns the centered fade create / notice / confirm modals, modal id constants, one shared select loading/render helper for domain and UTM source / medium, one Tags field with click-to-add recommended tag buttons plus removable selected chips inside the tag input, the Domain label-row "Custom domain?" action (manager passthrough to `/myDomain`, non-manager external link to `https://lihidomain.com`), the UTM source / medium row "Manage options?" action, separate confirm-before-dashboard messages for custom domains and UTM options, UTM collection for non-media items, hidden UTM controls plus blank UTM payload values for media / attachment items, and confirm callbacks. `lihi-button.js` owns delegated clicks on JS-created `button[data-lihi]` and administrator-only adjacent `button[data-lihi-edit]`, button rendering inside empty `data-lihi-container` nodes, `data-lihi-already` label state (`Create` vs `Copy`), copy/create/edit/dashboard-target flow orchestration, busy state, clipboard fallback prompt, opening the create modal only after `lihi_missing` copy errors, generating verifier/challenge for Edit and confirmed modal dashboard actions, selecting passthrough targets on the frontend (`/myDomain` for domain management, `/profile#utm-setting` for UTM settings, existing short URL for Edit), and opening lihi-admin's GET passthrough URL in a new tab with nonce + verifier query params.

UI registration hooks use anonymous callbacks; named settings and Short URL AJAX handlers are registered explicitly so each endpoint remains independently testable.
